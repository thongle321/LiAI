# 06: JobScheduler user-initiated job on API 34+ (WorkManager fallback kept)

**What to build:**

Port the reference scheduling shim (`DownloadScheduler.kt`, verified pins in the audit's engine-internals section): on API 34+, schedule the download first as a **JobScheduler user-initiated job** (`JobInfo.Builder(downloadId.hashCode(), DownloadJobService).setUserInitiated(true).setRequiredNetworkType(NETWORK_TYPE_ANY).setBackoffCriteria(30_000, BACKOFF_POLICY_EXPONENTIAL)`, extras for download id + progress interval, `setEstimatedNetworkBytes(totalBytes, NETWORK_BYTES_UNKNOWN)` when the total is known, `DownloadScheduler.kt:108-119`); when `scheduleUserInitiated` fails (throws → false), fall back to today's WorkManager path unchanged (`DownloadWorker.kt` enqueue, `NativeDownloadModule.kt` `enqueueUniqueWork("native-download-$id", REPLACE)`).

- Add the `DownloadJobService` (UserInitiatedJobService analog of the reference), porting `cancelRunners` semantics: cancel in-process run + WorkManager work + the UIDT job; `hasRunner` = run active || UIDT pending || WorkManager unfinished.
- Manifest: the user-initiated job needs `RUN_USER_INITIATED_JOBS` (reference `AndroidManifest.xml:12-16` carries INTERNET/RUN_USER_INITIATED_JOBS/POST_NOTIFICATIONS). LiAI's `android/` is committed and regenerated by `expo prebuild --clean` + `plugins/` — add the permission through a config plugin per AGENTS.md (never hand-edit `android/`), mirroring `plugins/withCameraUsesFeature.js`.
- This closes the audit's "10-minute cap" row: the reference survives multi-GB transfers by scheduler policy, not only by LiAI's foreground-service workaround; the foreground service stays as is.

Ship the ported tests first (port `DownloadSchedulerTest.kt` + `DownloadJobServiceTest.kt` shapes; Robolectric `Schedulers` shadowing): API-34 branch schedules UIDT first; schedule failure falls back to WorkManager; cancelRunners tears down all three runners; NetworkType still enforced by the WM fallback path.

## Resolution

- TDD verified red→green: the three new suites were written from the reference pins first, then made to pass. Final native state: **63 tests, 0 failures across 7 suites** (Dao 16, Engine 10, Migration 1, Worker 24, Scheduler 7, JobService 2, Runs 3). Invocation: `.\gradlew.bat :native-download:testDebugUnitTest`. The worker suite was NOT touched — its 24 tests passing through the extraction is the behavioral proof of the refactor.
- Extraction first: the entire transfer (`adopt`, `attemptTransfer`, `commit`, `restart`, the fail/auth helpers, and the `okhttp3.Call.await()` suspension) moved verbatim out of `DownloadWorker.kt` into new `DownloadRunner.kt`, parameterized by `stopped`, `progress` (replaces `setForeground` at the call site), `signal: StopSignal?`, and `progressIntervalMs`. `DownloadWorker.kt` became a thin host: claim → register `DownloadRuns` signal → setForeground → `runner.run(record)` → success/failure/retry per the returned `End`. The fallback request keeps its parity choices (CONNECTED constraint, 10 s exponential backoff floor) and NEW rides `KEY_PROGRESS_INTERVAL` in its input data.
- New `DownloadRuns.kt` (StopSignal + register/unregister/stop/isActive, ported verbatim — the reference's destination/start locks were dropped because LiAI's `casStatus` claim is already the serialization), `DownloadScheduler.kt` (RunnerScheduler/UtdtPort/WorkPort ports; `JobSchedulerUidt` @RequiresApi(34); `WorkManagerPort` enqueueUniqueWork REPLACE; `schedule()` = cancelRunners FIRST, then UIDT on 34+, else WorkManager fallback, mirroring `DownloadScheduler.kt:108-129`), and `DownloadJobService.kt` (`@RequiresApi(34)` JobService: threaded progress posts deduped on (title, percent), `jobFinished(reschedule)` exactly once via `running.remove(jobId, entry)` before the coroutine's finally, `stopKind`/`reschedules` ported verbatim, IOException → QUEUED + reschedule mirroring the worker ladder, SSL → FAILED row).
- Signal plumbing closes the audit's blocked-read hole: `DownloadRunner` writes `signal.call = call` after `client.newCall` and cancels a pre-stopped call (reference `attempt()` 179-181), so `captureRunners` from pause/cancel breaks an in-flight blocked read at once; the worker AND the JobService both run through the same runner with the same signal semantics.
- cancelRunners is three-layered (in-process `runs.stop` → UIDT `uidt.cancel(jobId)` → `work.cancel`), matching the reference order; `hasRunner` = active || UIDT pending || unfinished work. `hasRunner` is not exposed to JS yet — no consumer exists; the ported scheduler test pins it (`pendingUserInitiatedJobCountsAsARunner`). Module wiring: start/resume/retry → `scheduler.schedule(id, totals)` (resume/retry prefer the adopted `totalBytes`, falling back to the catalog estimate so `setEstimatedNetworkBytes` carries the real size); pause/cancel → `scheduler.cancelRunners(id)`.
- Acceptance-box divergence (box 3, deliberate): `RUN_USER_INITIATED_JOBS` went into the module's own `AndroidManifest.xml` next to the `POST_NOTIFICATIONS` precedent — which sits in the same file with that exact WHY (“declared here rather than in a config plugin so prebuild carries it through the module manifest merge with no extra wiring”) — rather than through a new config plugin mirroring `plugins/withCameraUsesFeature.js`. A module-owned permission belongs in the module's manifest; the substance of the box (prebuild-reproducible, never hand-editing committed `android/`) is satisfied either way, and no app.json/plugin surface is needed. `DownloadJobService` is likewise declared in the module manifest (BIND_JOB_SERVICE, exported=false).
- Dropped dependency: the reference's `cancelUniqueWork().result.await()` uses `androidx.concurrent.futures` (`ListenableFuture.await()` ktx), which is not on the module classpath (work-runtime only ships the `ListenableFuture` interface). `WorkManagerPort.cancel` therefore skips the await — `runs.stop()` already breaks the in-process run, and `hasUnfinished` uses a hand-rolled private `ListenableFuture.await()` suspension (suspendCoroutine + addListener) in `DownloadScheduler.kt`. No new dependency was added, per AGENTS.md.
- Tests ported: `DownloadSchedulerTest.kt` (Robolectric, `@Config(sdk=34)` + the `@Config(sdk=33)` fallback test; FakeUidt/FakeWork as in the reference; 7 tests — ADC-off skip covered by the sdk=33 case rather than a separate 8th), `DownloadJobServiceTest.kt` (stopKind mapping over every STOP_REASON + only-SYSTEM-reschedules), `DownloadRunsTest.kt` (3 signal-lifecycle tests) — all green.
- Code review (both axes): spec faithful, all five boxes independently re-verified (fresh `gradlew --rerun-tasks` run + typecheck), zero scope creep. Minor judgement calls recorded as follow-ups, not defects: the JobService exception ladder and the worker's are separate couplings of the same runner and could drift (an extraction was considered — judgement: don't, the reference keeps them separate too); `posted` in the JobService is main-thread-written but coroutine-read (the dedupe pair, benign for progress display); the JobService layer-tests cover the pure helpers only, the threading is exercised through the shared runner in `DownloadWorkerTest`.
