# 04: In-process retry loop + stall watchdog + Room migration v1→v2

**What to build:**

Port the engine's attempt loop and stall accounting into the worker, keeping LiAI's QUEUED-requeue discipline (never `dao.fail` while the run can still be rescheduled — the deliberate divergence recorded in the audit):

- Room migration v1→v2, declared here first and reused by ticket 05: add the columns the ported semantics need (`stalledRuns`, response `etag`, `totalBytes`, `createdAt`) and the DAO surface the reference compiles against — `casStatus`, `writeProgress` (returns row count), `writeValidators`, `byDestination`, `endTransientRun` (reference `DownloadDao.kt:18,30,45,48,54`; LiAI `DownloadEntity.kt` is v1 with none of them).
- Port the attempt loop (`DownloadEngine.kt:131-156`): retry transient attempts in-process with exponential backoff 2 s → 30 s cap, sleeping in 250 ms stop-aware steps; reset backoff to the initial value whenever bytes advanced since the last failure.
- Port the stall watchdog (`104-114`): if no byte arrived for `GIVE_UP_AFTER_MS` (120 s) the run gives up; a run that wrote bytes resets `stalledRuns` to 0, one that wrote none increments it; at `MAX_STALLED_RUNS` (5) the row fails with `STALLED_ERROR = "Download stalled: no data received"`, otherwise it requeues QUEUED.
- Route 408/429/5xx and `IOException` through this loop as transients (replacing their WorkManager `Result.retry()` hops — WorkManager stays as the process-death backstop, not as the retry curve), per the reference 408/429/5xx → `Attempt.Transient` (`respond()` 246).
- Keep the `Restart` (remote-changed) semantics plumbed for ticket 03 (the single-Restart guard lives in this loop: `restarted` set → second Restart fails the row with `REMOTE_CHANGED_ERROR`).

Ship the ported tests first: engine-loop tests with an injected scheduler clock (transient backoff curve, reset-on-progress, give-up at 120 s, stalledRuns counting at 0..6 runs), a MockWebServer 408-then-200 success case, and the v1→v2 migration test.

## Resolution

- TDD red→green verified: the red run failed to compile exactly on the new surface (unresolved `casStatus`/`writeProgress`/`writeValidators`/`stalledRuns`/`etag`/`totalBytes`/`createdAt`/`DownloadEngine`), then the implementation turned everything green. Final after code review: **36 tests, 0 failures** (DownloadDaoTest 16 + DownloadEngineTest 10 + DownloadMigrationTest 1 + DownloadWorkerTest 9). `npm run typecheck` clean.
- Code-review fixes folded in (two-axis sub-agents, standards + spec): production engine now sleeps in the 250 ms stop-aware steps the ticket claimed — `DownloadEngine.steppedSleep()` chunks any backoff into `SLEEP_STEP_MS` pieces and bails early when stopped; the worker's default engine uses it (injected test engines pass fast sleepers). `endTransientRun` gained the reference's `AND status = 'RUNNING'` guard and the worker consumes its row count — a pause/cancel racing the reschedule no longer resurrects a settled row QUEUED (engine returns `End.Stopped` when the reschedule writes 0; `reschedule` callback is now `(reason, stalledRuns) -> Boolean`); `failStalled` is likewise RUNNING-guarded via `casStatus(RUNNING → FAILED, STALLED_ERROR)`. Give-up semantics tightened to the reference's intent: `lastByteAt` re-anchors only on MARGINAL progress (bytes beyond the last failure), so an attempt rewriting the SAME stale offset can no longer push the watchdog out forever — that case gives up with bytes>0, which heals the pending stall count to 0 (test: `aRunThatWroteStaleBytesHealsTheStallCount`). The empty-body lane now writes its FAILED row (`failAttempt(record, "Empty response body")`) like every other terminal lane, and all terminal lanes share a `failAttempt` helper. New tests: `sleepStepsAreTwoFiftyMillisAndStopAware`, `aRunThatWroteStaleBytesHealsTheStallCount`, `aLostRescheduleRaceEndsStoppedNotRescheduled`, `endTransientRunRefusesANonRunningRow`.
- `DownloadEntity.kt`: schema v1→v2 — four columns with Kotlin-side defaults and `@ColumnInfo(defaultValue = ...)` so the generated schema matches the migration: `stalledRuns INTEGER NOT NULL DEFAULT 0`, `etag TEXT`, `totalBytes INTEGER`, `createdAt INTEGER NOT NULL DEFAULT 0`. DAO gains the reference surface: `casStatus` (compare-and-set out of entry states), `writeProgress` (RUNNING-guarded, writes bytes + totalBytes, heals `stalledRuns` to 0, returns row count), `writeValidators` (pins etag/totalBytes/offset), `byDestination` (newest first by createdAt), `endTransientRun` (QUEUED reschedule carrying the stall count). Migration note: written against Room-KMP's `migrate(SQLiteConnection)` overload (not `SupportSQLiteDatabase`) because the test suite opens the database through the Bundled SQLite driver.
- New `DownloadEngine.kt`: the pure attempt loop — attempt-until-terminal over injected callbacks (clock, sleeper, attempt, reschedule, failStalled), no DB/HTTP inside. Reference order preserved per transient: progress-reset → give-up check → sleep. Backoff `2 s → 30 s` cap; give up at `120 s` without bytes; `stalledRuns` counter (0-byte run increments, writing run heals to 0; ≥ 5 → `End.Failed("Download stalled: no data received")` via `failStalled`, otherwise `endTransientRun` → QUEUED + `End.Rescheduled`); single-Restart guard → second Restart fails with `"Remote file changed during download"` (ticket 03 exercises it).
- `DownloadWorker.kt`: gains the 4th injected `engine` param (2-arg constructor untouched). `run(record)` now claims the row with `casStatus(QUEUED|RUNNING → RUNNING)` before looping (0-claim → `Result.success()` — a CANCELLED/PAUSED/terminal row is not work), then drives `engine.run(...)`: attempt is the old `transfer()` body renamed `attemptTransfer(record): Attempt`; the 408/429/5xx lane returns `Attempt.Transient("HTTP $code", 0)` and IOException inside the attempt returns `Attempt.Transient(io.message, net bytes this attempt)` — no WorkManager `Result.retry()` for these anymore, WorkManager is the process-death backstop only; `SSLPeerUnverifiedException` is rethrown out of the attempt and stays terminal in doWork. The 1 Hz progress publish switched to the row-count-returning `writeProgress` — 0 means the row left RUNNING under us and the attempt ends as `Attempt.Stopped` (bytes kept). Finding worth keeping: the RUNNING claim was required because `writeProgress` is RUNNING-guarded; the old unconditional `mutate(status = RUNNING)` used to promote QUEUED → RUNNING silently.
- `NativeDownloadModule.kt`: `createdAt = existing?.createdAt ?: System.currentTimeMillis()` on enqueue — REPLACE keeps the row's birthdate (ticket-05 supersede orders by it).
- `DownloadStore.kt`: thin suspend delegates for the five new DAO methods.
- Deliberate divergence (recorded): a plain transient keeps the row RUNNING and stays in-process — the reference reschedules through the controller and would pause with QUEUED between in-process attempts; QUEUED writes happen only at give-up reschedules. Also `endTransientRun` never writes FAILED (QUEUED discipline).
